# 从零构建 Web 动画（animate）

> 一句话：你说「这里加个动画」，它按决定成败的顺序做七个决策，然后**写出能一次通过严格评审的实现代码**——有时候答案是一行都不写。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零依赖。技能本身不装任何包：默认用原生 CSS / CSS `@starting-style` / WAAPI，只有在需要弹簧、布局动画、退场动画或手势时才建议引入 `motion.dev`（Motion）。面向 Web 前端。 |
| 产出 | 可直接落地的动画实现代码（CSS 或 JSX），外加**最多几行**的说明：门禁结果（频率档位 + 命名目的）、配料清单（工具/属性/曲线/时长或弹簧参数）、以及哪些只能靠手感验证。不是报告，代码才是交付物。 |
| 入选理由 | 它逼你在写 `cubic-bezier` 之前先回答「这该不该动」。第一步和第二步就是门禁，**产出零行代码是成功而不是推脱**。它还明确了模型最容易犯的两类错：给不该动的东西加动画；以及配料错（进场用 `ease-in`、`scale(0)`、toast 上用 keyframes、让下拉显得迟钝的时长）。所有曲线、时长、弹簧参数必须取自技能里的表格，不许凭印象编一个 `cubic-bezier(0.4, 0, 0.2, 1)`。 |

## 它解决什么问题

多数「加个动画」的请求会得到一个看起来很动、但手感不好的实现。这个技能的开场定位很窄：**它只做一件事**——把动效请求变成能扛住严格评审的实现。它不审计代码库（那是 `improve-animations`）、不批评某个 diff（那是 `review-animations`）、不找哪里该动（那是 `find-animation-opportunities`）、也不做 React Native（那是 `animate-expo`）。

它把施工拆成**七个必须按顺序走的步骤**：

1. **该不该动**——按频率分档：100+ 次/天（键盘快捷键、命令面板开关）**永远不做，直接停在这里**；几十次/天只能做「几乎察觉不到」的；偶尔出现（弹窗、抽屉、toast）才用标准动画；罕见/首次（引导、成功、庆祝）才是「惊喜预算」该花的地方。**键盘触发的动作是取消资格，不是判断题**，拿 Raycast 没有开合动画当正面例子。如果请求过不了这道门，技能要求**直说并给出不动的替代方案**（瞬时状态变化、静态可供性提示）。
2. **目的是什么**——必须能用这六个词之一命名：feedback、spatial consistency、state indication、preventing a jarring change、explanation、delight（仅限罕见档）。命名不了就不做。「看着酷」用在常看到的元素上，是停下来的理由。
3. **挑工具——能用的最便宜那个**——从上往下走：hover/按压/颜色/类名控制的状态切换 → **CSS transition**；挂载即进场且无 JS 状态 → **CSS `@starting-style`**；页面忙着加载时也不能卡 → **CSS animation**（跑在主线程之外）；要程序控制又要 CSS 性能 → **WAAPI `element.animate()`**；弹簧、布局动画、退场、手势驱动值 → **Motion**。如果需求其实是「要一个组件」（toast、drawer、命令菜单、dropdown），技能明确说停下，改用 `pick-ui-library`——手搓这些正是得到一个没有焦点管理的 `<div>` 下拉的原因。
4. **挑属性**——只动 `transform` 和 `opacity`（`clip-path` 是被特批的第四个；`height` 只在手风琴里被容忍）；绝不 `scale(0)`，从 `scale(0.9–0.97) + opacity: 0` 起步；popover / dropdown / menu / tooltip 的 `transform-origin` 要放在触发点上（`var(--transform-origin)`，modal 豁免）；`translate()` 用百分比（`translateY(100%)` 按自身高度走）；用 Motion 时写完整 transform 字符串而不是 `x`/`y`/`scale` 简写，否则高负载下掉帧；**不要用父级上的 CSS 变量驱动子元素 transform**——那会重算每个子元素的样式。
5. **缓动与时长，或者弹簧**——进场/退场 `ease-out`；屏幕上移动/形变 `ease-in-out`；hover/颜色 `ease`；匀速（跑马灯、进度条）`linear`。**UI 里永不用 `ease-in`**。内置缓动太弱，用三条 token：`--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`、`--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`、`--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1)`；不够用就去 easing.dev 或 easings.co 拿，**不要自己手搓**。时长：按钮按压 100–160ms、tooltip 125–200ms、下拉/选择 150–250ms、弹窗/抽屉 200–500ms，**UI 动画守住 300ms**。带惯性拖拽、要「活着」的元素、用户能中途打断/反向的手势、装饰性鼠标跟随——这些改用弹簧，Apple 式 `{ type: "spring", duration: 0.5, bounce: 0.2 }` 或传统 `{ mass: 1, stiffness: 100, damping: 10 }`，bounce 控制在 0.1–0.3。
6. **打断与退场**——快速反复触发的东西（toast、开关）用 transition 不用 keyframes，因为 transition 从当前值重新瞄准、keyframes 从零重来；手势配弹簧，因为弹簧能在打断时把速度带过去；**从哪进就从哪出**（底部滑入的 toast 从底部离开，对称路径才让滑动关闭显得理所当然）；用户在做决定的阶段可以慢（长按确认 2s linear），系统回应要快（松手 200ms ease-out）。
7. **减弱动效与指针门禁随动画一起交付**——`prefers-reduced-motion` 意味着**更少更轻**而非全关（保留帮助理解的透明度/颜色，去掉位移）；`@media (hover: hover) and (pointer: fine)` 包住 hover 动画，因为触屏点按会触发假 hover。

## 什么时候该用它

- 「给这个按钮加个按压反馈。」
- 「做一个从按钮长出来的下拉菜单。」
- 「帮我写个 toast 的进出场。」
- 「这个抽屉做成可以拖拽关闭的。」
- 「列表加载出来的时候让它们依次出现。」
- 「手风琴展开动画怎么写？」

## 什么时候别用它

- 批评已有动画、逐条判定合格与否 → `review-animations`（`animate` 的门禁和它的标准是同一套）。
- 审计整个代码库、出改进路线图 → `improve-animations`。
- 找「哪里该动却没动」→ `find-animation-opportunities`。
- React Native / Expo 里的动画 → `animate-expo`。
- 需求其实是「要一个 toast / drawer / command menu 组件」而不是一段动画 → `pick-ui-library`。
- 要的是触屏 Web 的原生手感（粘住的 hover、100vh 的坑等）→ `mobile-native`。

## 怎么开口

- 「给搜索框做一个聚焦时的下拉建议，用 CSS 就行别装库。」
- 「这个 toast 从底部滑入，退场该怎么处理？」
- 「我想做一个长按 2 秒才触发的删除按钮。」
- 「标签页切换时指示器要平滑跟过去，颜色也要跟着变。」
- 「这个拖拽关闭抽屉的动画，速度阈值你帮我定。」
- 「我们代码库里已经有 `--ease-out` 这个变量了，用现有的。」

## 输入 / 输出

输入：一句话动效需求（通常附带现有代码、组件名、已有的设计 token）。技能**没有前置提问清单**，直接判断并实现；只有在过不了第 1 步门禁时才回头跟你说不做。

输出结构被固定：先写代码，然后用最多几行交代三件事——
- **门禁结果**：频率档位 + 命名的目的；如果请求里有东西被否了，说清否了什么、为什么。
- **配料**：工具、属性、曲线、时长或弹簧参数，一行一个。
- **需要靠手感验证的部分**：代码里判断不了的东西（crossfade、弹簧的弹跳、进场列表里 opacity 与 height 的平衡），要明说并给出验证方法——把时长放到 2–5 倍播放、用 DevTools 的 animation inspector、逐帧步进、在真机上试手势、第二天用新鲜的眼睛再看一遍。

技能明确要求「不要把这个扩写成一份报告。代码才是交付物」。语气要求：**有主见、简短**；诚实的答案是「这不该动」时就给这个答案；手感真的判断不了时就说判断不了，而不是瞎猜一个数值。

## 依赖与前提

- 无网络、无 CLI、无必装 npm 包。
- **第 3 步的硬性偏好是「能用的最便宜的工具」**：一个淡入不值得为它装一个 motion 库。
- 只有在需要弹簧、布局动画、退场动画或手势驱动值时才会用到 Motion（`motion.dev`）；程序化控制可以先用 WAAPI。
- 若浏览器不支持 `@starting-style`，退回挂载标志位模式（`useEffect` 里 `setMounted(true)`，配 `data-mounted` 属性）。
- 强约束：**扩展代码库已有的 token，不要另起一套**。如果项目里已经有 `--ease-out` 或时长刻度，必须用现有的——新增平行体系属于缺陷。

## 内部结构

技能包由两个文件组成，按渐进披露切分：

- **`SKILL.md`（209 行）**——主张、门禁与决策。结构是：Operating Posture（两种失败模式，第一种更糟：给不该动的东西加动画）、5 条 Hard Rules（严格按顺序走；不许用近似值；扩展而非分叉 token；减弱动效和 hover 门禁随动画交付；用能用的最便宜工具）、The Build Sequence（上面那七步，含三张决策表：频率表、工具表、缓动表 + 时长表）、Never Ship 自检表（13 行）、Output、Tone。
- **`RECIPES.md`（324 行）**——可直接开工的实现。`SKILL.md` 原文点名了 12 个配方：button press、dropdown/popover/menu/select、tooltip、modal、drawer/sheet、toast、accordion、stagger、hold-to-confirm、tab indicator、scroll reveal、drag-to-dismiss；文件里还多两条实战技巧——`Masking a crossfade that won't settle`（用 `filter: blur(2px)` 弥合调不好的 crossfade，上限 20px）和 `Programmatic, without a library`（WAAPI 写法）。文件开头声明所有曲线都复用 `SKILL.md` 里的三条 token，并强调「从配方开始改，不要从空文件重建」。

最有价值的一处机制是**第 1、2 步构成门禁**：门禁不过，后面五步根本不执行。第二处是 **Never Ship 表**，它等于把 `review-animations` 的自动阻断项提前告诉你，让你第一次就写对。

## 注意事项与已知限制

- **`Never Ship` 自检表是硬性红线**（原文：每一条在 `review-animations` 里都是自动阻断项）：`transition: all`；`scale(0)` 进场；UI 元素上的 `ease-in`；需要刻意感的动画用内置 `ease-out`；键盘快捷键或每天 100+ 次的动作上加动画；无理由超过 300ms；触发点锚定的 popover 用 `transform-origin: center`；toast/开关等快速触发元素上用 keyframes；动 `width`/`height`/`margin`/`padding`/`top`/`left`；Motion 的 `x`/`y`/`scale` 简写；未加门禁的 `:hover` 位移动画；缺 `prefers-reduced-motion`；所有元素同时进场（应加 30–80ms 阶梯）。
- **不要给用户一菜单的方案**——技能要求「做决定、一行说明理由、写代码」。
- 技能会**主动拒绝**：门禁不过时它给替代方案而不是硬写；手感判断不了时它说判断不了。
- 它是施工技能，会写代码，但**不会自动改动你的代码库**——实现以代码块形式交付，落地由你决定。
