# UI 多方案原型（prototype）

> 一句话：把你描述的一个 UI 部件（一个 toast、一张定价卡、一个长按删除按钮）做成 3 个**真正不同**的版本，放在一个悬浮切换器后面，让你现场翻着选，选完再帮你并进代码。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零依赖（不联网、不装 CLI）。有项目时在你的 dev server 上加一条隔离路由；没项目时产出一个单文件 HTML，直接用浏览器打开 |
| 产出 | 一个可视切换的原型面：一个 variant 一个文件 + 一个小 harness（或单文件 HTML），外加一张「变体 / 分歧轴 / 何时选它 / 代价」的对比表；选定后再集成进代码库 |
| 入选理由 | 模型的默认行为是「给你一版最好的方案」。而设计探索真正缺的是**分歧**——同一个想法换个色调凑三版毫无价值。这个技能把「必须真正不同、且每版单独都够格上线」写成了硬规则，还配了一个固定的切换器规范和 `riff` / `keep` 的交互语法，这件事模型自己不会主动做 |

## 它解决什么问题

它的定位很窄，只有一件事：**发散（divergence）**。技能开头就划清边界：它不评审已有 UI（那是 `review-animations`）、不为已有 UI 规划修复（那是 `improve-animations`）、也不选依赖（那是 `pick-ui-library`）。

核心主张是：**三版同一个想法的不同色调是在浪费这个切换器**——你翻来翻去什么也学不到。每一版都必须是你**能单独辩护说可以上线**的一个方向，是对同一份 brief 的**真正不同的回答**。而且发散不是降低工艺标准的借口：每一版单独都要满足 Emil Kowalski 的那套标准——进场用 `ease-out`（绝不用 `ease-in`）、UI 动效低于 300ms、正确的 `transform-origin`、只动 `transform`/`opacity`、处理 `prefers-reduced-motion`。一个糙的变体不会拓宽探索，它只会在执行上输掉，让你对这个方向什么也了解不到。

为了保证「不同」，它要求**分歧必须落在一条命名的轴上**：布局、密度、性格、动效、交互模型。动手前你必须能用一句话说出每一版的分歧轴；名字要描述方向（"Quiet"、"Editorial"、"Playful"、"Dense"），**绝不能叫"选项 A/B/C"**。判定标准写得很硬：如果两个方向只差强调色或文案，它们是**一个**方向，必须换掉一个。完成条件是「每版都有名字和轴，且没有两版共用同一个轴位置」。

工作流分六阶段：① **Scope**（一次只做一个东西；如果描述跨越多个组件，比如「整个仪表盘」，要收窄到最有杠杆的那一个，说明为什么，其余留作后续）→ ② **Recon**（摸清技术栈、设计令牌、产品性格、上下文；**没有项目就跳过**并选一套克制的默认外观：中性灰 + 一个强调色 + 系统字体）→ ③ **选方向**（默认 3 版，用户要求或空间确实宽时最多 5 版，**超过 5 版会稀释比较**）→ ④ **搭 picker 骨架**（有 dev server 就开隔离路由 `/prototypes/<slug>`，一版一文件；没项目就出单文件 HTML）→ ⑤ **验证并交付**（跑起来自己先翻一遍，确认每版都渲染、交互都有反应、控制台干净；然后给出对比表并**停下——选择权属于用户**）→ ⑥ **按选择提升**（集成到你选的那版该在的位置，遵循项目既有约定，然后删掉原型面）。

两条容易忽略的体验规则：harness 必须**一次只渲染一版、全尺寸、带真实周边上下文**（toast 背后要有页面，卡片要有兄弟元素，按钮要有表单）；**不要用缩略图并排比较**，那会扭曲间距和尺度——技能原话是「绝不要在邮票大小上评判 UI」。切换必须是**瞬时的**：翻看是一次数以百计的动作，按频次原则，变体切换不加任何动画。

## 什么时候该用它

> ⚠️ 这个技能的 frontmatter 里有 `disable-model-invocation: true`——意思是**它只能由用户显式调用，不会被自动触发**。你要用它得自己开口，通常是在对话里打 `/prototype`（或点名这个技能）。

- 「/prototype 帮我做几个版本的定价卡」
- 「/prototype 这个 toast 我想看几种不同的做法」
- 「/prototype 长按删除按钮，给我 5 个方向」
- 「/prototype riff Editorial — 沿着这个方向再来一轮」
- 「/prototype keep Quiet — 就它了，并进代码」
- 「/prototype keep Playful，但把 picker 留着」

## 什么时候别用它

- 要**评审现有动画代码**用 `review-animations`；要**规划修复路线图**用 `improve-animations`；要找**该动没动的地方**用 `find-animation-opportunities`（技能里逐一点名了这三个）。
- 要**选依赖库**用 `pick-ui-library`。
- 要直接交付单一成品设计、或按 anti-slop 门审计页面，用 `design-toolkit`。
- 需要的是**做演示文稿**（用 `univer-slide`）或后端/数据库/业务逻辑（不在范围内）。

## 怎么开口

- 「/prototype 我要一个订阅升级的 toast 提示」
- 「/prototype 设置页里的开关行，给我 3 个真正不同的方向」
- 「/prototype 这个空状态卡片，来 4 版」
- 「/prototype riff Quiet」
- 「/prototype keep Dense」
- 「/prototype keep Editorial, leave the picker」

## 输入 / 输出

输入：一句你要做的 UI 部件描述，可能带数量后缀（`x5`）。技能会按需做侦察（技术栈、令牌、性格、上下文），必要时收窄范围并说明为什么。

输出：一个可现场切换的原型面（隔离路由或单文件 HTML），加一张对比表和运行地址/文件路径与翻页按键说明。**对比表固定为四列**：`# | Variant | Axis | When it's the right choice | Its cost`，例如「1 Quiet / 动效极少、用边框代替阴影 / 产品是日常使用工具 / 最不容易被记住」「2 Editorial / 大字号、留白充足 / 这个时刻值得有分量 / 吃掉纵向空间」。**结尾要给出 picker 运行在哪里（URL 或文件路径）和翻页按键。**

语气要求也有明文：诚实地推销每一版——一句说它什么时候赢，一句说它的代价；**永远不要在表里预先挑好赢家**；如果用户问你选哪个，要用产品性格和使用频次给理由，而不是纯审美。**如果两版在实现中收敛了，就砍掉一个并说明**——两个真正不同的方向胜过凑数的三个。

调用语法（`Invocation Variants`）：

| 调用 | 行为 |
|---|---|
| `<描述>` | 完整流程：scope → recon → 3 版 → picker → 等你选 |
| `<描述> x5` | 同上，指定版数（上限 5） |
| `riff <变体名>` | 新一轮：保留 harness，围绕指定方向的周边重新发散 |
| `keep <变体名>` | 把那版提升进代码库，并删除原型面 |
| `keep <变体名>, leave the picker` | 提升，但保留原型面 |

技能规定了固定开场白：**第一次被调用且你还没提具体问题时，只回一句**：

> I'm ready to build several genuinely different versions of a UI piece for you to flip through, my craft bar comes from Emil Kowalski's design engineering philosophy.

然后必须等你提问才能继续说。

## 依赖与前提

- 零外部依赖，不联网、不装 CLI。
- **有项目**：需要有 dev server，能在上面加隔离路由（文件命名/框架等价物按项目来）。
- **无项目**：产出单个自包含 HTML 文件（内联 CSS/JS），浏览器直接打开即可。
- 若环境里有浏览器工具，技能会要求给每版截图做验证。
- 工艺前提是参考 Emil Kowalski 的设计工程标准（本系列有 `emil-design-eng` 主技能）。

## 内部结构

目录里有两个文件，是「流程 + 铁打的规范」的切分：

- **`SKILL.md`（约 100 行）**：主流程。开场白、Operating Posture（发散为纲）、**Hard Rules 五条**、Workflow 六阶段、Invocation Variants 语法表、Tone 三条。
- **`PICKER.md`（约 197 行）**：切换器的完整规范，含 Markup、**逐字指定的 Styles（约 100 行 CSS）**、Rules 四条、Behavior contract、以及一段可直接用的 Reference wiring（约 55 行 JS）。

`PICKER.md` 之所以独立且要求**逐字照抄**：切换器的外观**不是设计决策**，它是 harness 的「浏览器 chrome」，必须每次、每个项目长得一模一样，才不会被认为是「被评判的设计的一部分」。它被设计成一个**底部居中的深色玻璃胶囊**——深色在任何页面（亮或暗）上都成立，所以它刻意不跟随主题，也不允许换成项目的字体、品牌色或令牌。

其中值得记住的细节：高亮条在按钮间滑动用 `transform 250ms cubic-bezier(0.23, 1, 0.32, 1)`，但**只在首帧后启用**（`data-ready`），避免加载时也动一下；被预览的变体切换仍是**瞬时无过渡**；高亮条的 `width` 过渡是**对 transform/opacity 规则的刻意例外**（元素仅 28px 高、绝对定位、无布局依赖，绘制成本可忽略）。行为契约：数字键 `1–N` 与 `←`/`→` 切换，`R` 重播；焦点在 input/textarea/select/contenteditable 里或按住修饰键时忽略按键；任何时刻只有一个项带 `data-active` 和 `aria-current="true"`；选择通过 URL 参数（`?v=2`）跨刷新保留，回退到第 1 版；切换会**重新挂载**变体，所以进场动画会重跑。

## 注意事项与已知限制

- **五条硬规则**：① 探索期间**绝不碰生产代码**，一切只在隔离的原型面里，集成只发生在第 6 阶段、且只对你选中的那版；② 变体必须在**命名的轴**上分歧，动手前要能说出每版的轴（共用项目令牌不算收敛，变体**本该**看起来属于这个产品）；③ **每版都要完整可用**：真交互、真动效、真实内容——像样的产品文案、可信的名字和数字，**不许 lorem ipsum、不许死按钮、不许"这部分你自行想象"**；④ **切换器是 chrome，不是参赛者**，逐字照抄，外观不许改；⑤ 选定后**清理**原型面，除非用户要求保留。
- 唯一的允许改动：如果某版占据屏幕底部中央（toast 堆叠、底部面板、dock），给 picker 设 `data-position="top"`，免得挡住作品；**除此之外不许移动或更改任何东西**。
- 重播按钮是**条件渲染**的：只有当至少一版有值得重播的进场/状态动画时才渲染它和分隔线，纯静态比较就是短一截的胶囊。
- 一次只做一个部件；范围太宽时要先收窄并说明理由。
- 超过 5 版会稀释比较，技能明确设了上限。
- 原型面（文件/路由）由它创建，选定后按规则删除——**这是它少数会自动改动文件的地方，且发生在你选定之后**。
