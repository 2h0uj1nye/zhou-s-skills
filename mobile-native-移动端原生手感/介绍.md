# 移动端原生手感（mobile-native）

> 一句话：把「在手机上看起来就是个网页」的那些破绽一条条拆掉——粘住的 hover、点按高亮、100vh 的坑、输入框放大页面、300ms 点击延迟、下拉刷新抢滚动、刘海遮内容、长按选中按钮文字、轮播方向乱、状态栏配色不匹配；大多是一行 CSS 或一个 meta 标签的事。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零依赖。不需要联网、CLI 或 npm 包；修复本身只用到标准 CSS/meta 标签。但**验证需要一部真手机**（USB 连接 + 局域网 IP 访问 dev server） |
| 产出 | 直接改好的代码（它是个 fix-it skill，不是报告技能）+ 结尾不超过几行的三条说明：哪里错了 / 改了什么（文件 + 声明，一行一条）/ 哪些必须上真机确认 |
| 入选理由 | 治的是「Chrome 里一切正常，一到手机上就散架」。这些 bug 在 Chrome 的设备模拟里**根本不复现**，所以模型（和你）都容易以为已经修好了。它给出的全是平台层的一行修复，并且反复强调「别用 JS 解决 CSS 能解决的事」——这是模型最容易搞错的方向 |

## 它解决什么问题

大多数「这个 app 在手机上很卡」的报告**不是动画问题**——是 300ms 的点击延迟、点按时的灰块闪烁、或者一个怎么也不肯松开的 hover 态。这个技能做的就是把这些平台层的破绽一条条删掉：viewport、触摸、滚动、安全区、浏览器 chrome——就是这几十行决定 app 感觉像「装上去的」还是「嵌在网页里的」。

技能点出两种失败模式，**第一种更糟**：

1. **只修桌面能看见的东西** —— 这个技能里的 bug 在 Chrome 的设备模拟里不会复现。只在那里测，就等于把它们全部发布出去。
2. **CSS 或一个 meta 标签就能搞定的事，却去写 JavaScript** —— 这里几乎每一条都是一行声明。「写个 `useIsTouchDevice()` hook 来隐藏 hover」是错的工具，**媒体查询才是对的**。

姿态上它假定你是那种被下面每一项都烫过的资深设计工程师，并且坚持：**用户的手机才是真相来源**。跑不到真机上，就明说哪几条能从代码验证、哪几条必须真机。

## 什么时候该用它

- 「帮我把这个 Web app 做得像原生 App」
- 「在 Chrome 里正常，但手机上不对劲」
- 「手机上点按感觉慢半拍 / 有灰块闪一下」
- 「底部按钮被地址栏挡住了 / 内容被刘海遮住」
- 「做 PWA / 底部弹层 / 轮播 / 全屏布局 / 任何触控交互」
- 「手机上 hover 效果点一下就粘住了」

## 什么时候别用它

- **要设计动画本身**（该不该动、什么曲线、什么时长）：用 `animate`。
- **要评审动画**：用 `review-animations`。
- **要做 React Native / Expo**：用 `animate-expo`。
- 它只管**平台层**——viewport、触摸、滚动、安全区、浏览器 chrome；不负责设计动效。

## 怎么开口

- 「这个 app 在手机上感觉像个网页，帮我弄得更原生一点」
- 「手机上有个灰色的点击高亮，怎么去掉？」
- 「iOS 上点输入框，整个页面被放大了」
- 「底部固定的按钮被 Safari 的地址栏挡住了」
- 「我这个横向轮播在手机上会上下抖」
- 「帮我按 mobile-native 的 Never Ship 清单自查一遍」

## 输入 / 输出

**输入**：你的 Web app 代码 + 手机上观察到的症状。技能给了一张 **Symptom Table** 让你先对号入座，再读对应章节看原因和确切代码。

**输出是代码本身**（"The code is the deliverable."），后面只跟**最多几行**的说明：

- **What was wrong** —— 对照症状表匹配到的症状，加一句为什么。
- **What changed** —— 文件和声明，一行一条。
- **What needs a phone** —— 哪些你能从代码验证，哪些必须用户在真机上确认。

**明确要求不要把这几行灌水成一份报告。** 首次被调用且没有具体问题时，固定开场白只回这一句：

> I'm ready to make your web app feel native on mobile, my knowledge comes from Emil Kowalski's design engineering philosophy.

## 依赖与前提

技术上零依赖，只需要改 CSS 和 HTML meta。但**验证需要真硬件**：手机 USB 连接、dev server 跑在 `0.0.0.0`、用机器的局域网 IP 打开；iOS 用 Safari → Develop → 设备，Android 用 `chrome://inspect`。技能要求用一部**几年前的老手机**测，而不是桌上最新那台；要**开着键盘测**，**横屏也要测一次**；如果 PWA 是目标，还要以**已安装**的形态测（standalone 模式会改变 viewport、安全区和状态栏行为）。Xcode Simulator 比模拟器强一档，但仍然测不出触感——真机才是标准。

## 内部结构

只有 `SKILL.md` 一个文件。正文分块：**Initial Response**（固定开场白）→ **Operating Posture**（两种失败模式）→ **Hard Rules（5 条）**→ **The Symptom Table（11 行，入口）**→ **The Fixes（11 条，每条带 why 和确切代码）**→ **Baseline（起步模板）**→ **Never Ship（12 行自查表）**→ **Output**→ **Tone**。

**五条硬规则**：① **每个修复都要带上理由**——按 why 适用处应用，而不是习惯性全局套（`user-select: none` 放在正文上是缺陷，放在按钮上是对的）；② **媒体查询优先于设备嗅探**——`(hover: hover)`、`(pointer: fine)`、`env()`、`dvh`，**绝不根据 user agent 或屏宽去猜触控**；③ **触摸和鼠标不是互斥的**——iPad 带触控板、笔记本带触摸屏、手机接鼠标，按**能力**门控而不是按设备；④ **绝不禁止缩放**——`user-scalable=no` 和 `maximum-scale=1` 是可访问性失败，改成修输入框字号；⑤ **宣布完成前必须在真硬件上测过**。

**11 条修复**（每条都给了确切的一行代码）：① hover 粘住 → `@media (hover: hover) and (pointer: fine)` 包裹（Tailwind v4 的 `hover:` 已自带，v3 设 `future.hoverOnlyWhenSupported`）；触摸用户靠 `:active` 拿反馈；② 点按灰/蓝闪 → `-webkit-tap-highlight-color: transparent`（全局设一次，然后必须给每个可点元素补自己的 `:active`）；③ 高度不对 → app 外壳用 `100dvh`、hero 用 `100svh`（`lvh` 几乎永远不要）；④ 输入框放大页面 → `font-size: 16px` 起步，顺带设置键盘（`inputmode`、`type`、`autocapitalize`、`autocorrect`、`enterkeyhint`）；⑤ 点按迟钝 → 两个原因叠加：300ms 延迟用 `touch-action: manipulation`，以及在**按下**而不是松开时给反馈（`:active` / `pointerdown`，100–160ms、`ease-out`）；⑥ 下拉刷新抢滚动 → 根上 `overscroll-behavior: none`，内层滚动容器用 `contain`；**绝不要用 `touchmove` + `preventDefault()`**；⑦ 内容被刘海截断 → `viewport-fit=cover` + `env(safe-area-inset-*)`（少了 meta 标签 `env()` 全是 `0px`）；⑧ 长按选中按钮文字 → `user-select: none` 只给控件（含 `-webkit-` 前缀和 `-webkit-touch-callout`），**绝不放在 `body` 上**；⑨ 轮播方向乱 → `touch-action: pan-y` / `none` / `pan-x`（值说的是「浏览器还能做什么」）；原生滚动的话优先 `scroll-snap-type: x mandatory`；⑩ 状态栏不匹配 → 每个 `prefers-color-scheme` 一个 `theme-color`；⑪ 真机才是标准。

还有一份可以直接抄的 **Baseline** 起步模板（viewport meta 含 `interactive-widget=resizes-content`、两条 `theme-color`、`html {-webkit-tap-highlight-color: transparent; -webkit-text-size-adjust: 100%; overscroll-behavior: none;}`、`input/textarea/select { font-size: 16px; }`、按钮的 `touch-action` 和 `user-select`、以及一个空的 `@media (hover: hover) and (pointer: fine)` 块），和一张 **Never Ship** 自查表（12 行「绝不要 / 改成什么」）。

## 注意事项与已知限制

- **大多是一行修复**：技能强调「说这一行和理由，然后继续」，别把它写成报告。
- **必须上真机**：所有列出的 bug 在设备模拟里都不复现；跑不到硬件时要**明说哪几条没验证**，而不是声称已修好。
- **会拒绝你的错误修法**：`user-scalable=no` / `maximum-scale=1` 被明确列为可访问性失败；`user-select: none` 放 `body` 上是缺陷；用 `touchmove` + `preventDefault()` 阻止 overscroll 会完全阻断滚动并让监听器变成非 passive、掉帧；`touch-action: none` 放在用户需要滑过去的东西上会把人卡住。
- **不要用 user agent 嗅探判断触控**——用 `(hover)` / `(pointer)`。
- **不要写 hook 隐藏 hover**——用媒体查询。
- **调动的边界**：它只修平台层，不动效设计，不做 React Native。
