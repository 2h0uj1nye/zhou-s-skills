# Requirements Planning — 从模糊意图到可验证规格与任务卡片

## 定位与边界

- **做**：把一句话的模糊意图逼成可验证的规格，再把规格拆成字段完整的任务卡片。
- **不做**：不写代码、不实现、不排期、不做任务调度。依赖编排与执行交给宿主已有的 plan mode / AgentTeams —— 本技能只保证**交给它们的输入是干净的**。
- **失败的样子**：交付物看起来整齐，但每条验收标准都无法判定真假；或卡片缺字段，下游必须回头再问一次。这等于没做。

## 三个模式

| 模式 | 何时进入 | 产物 | 细则 |
|---|---|---|---|
| A 反问澄清 | 需求含混、宏大、或只有一句话 | 澄清记录 + 假设清单 | `references/interrogation.md` |
| B 写规格 | 意图已清楚，但没成形 | 规格文档（功能/约束/接口/验收） | `references/spec-template.md` |
| C 拆任务卡片 | 规格已确认 | 任务卡片集 | `references/ticket-template.md` |

路由规则：

1. 用户直接要规格 → 先跑 A 的**最小版**（只问阻塞项，≤3 个问题），再过 B。
2. A 的**停止判据**不满足，就不得进入 B。宁可交付“澄清记录 + 假设清单 + 风险标注”，也不要交付一份编出来的规格。
3. 用户只给了规格要拆卡片 → 直接 C，但先做规格体检（验收标准是否可判定），不合格则退回 B 补。
4. 只做用户要的那一段，不要自动把 A→B→C 全跑完。

## 【输入】

必需：

- 需求原文（用户原话，不要提前润色）。
- 已知的硬约束（预算、deadline、已有系统/接口、合规要求、技术栈锁定）。

可选（缺了就走降级路径，不要追问超过 2 轮）：

- 目标用户与使用场景、成功指标基线、现有方案与它的痛点、相关文档或代码位置。

## 【输出】

按模式产出，落成 Markdown 文件（默认放在用户指定的路径；未指定则放在当前工作目录，文件名如 `spec-<主题>.md`、`tickets-<主题>.md`）：

- A：`澄清记录`（问过什么、答了什么、哪些没答上）+ `假设清单`（含影响与复查触发点）。
- B：规格文档，含功能列表 / 约束条件 / 接口定义 / 验收标准 / 假设与风险 / 脱敏提示 / 变更记录。
- C：任务卡片集，每张卡片的必填字段齐全（见 `references/ticket-template.md`）。

## 【步骤】

### A 反问澄清

1. 复述你理解的需求（一句话），让用户确认或纠正。**先复述再提问**，否则问的是你脑补的那版。
2. 按 `references/interrogation.md` 的五类问题筛一遍：伪需求 / 约束与偏好 / 失败模式与边界 / 验收预演 / 范围取舍。
3. 一次最多问 3–5 个问题，**给候选选项 + 你的默认建议**，不要开放式丢问答题。
4. 同一问题最多追问 2 轮；第 3 轮改为“这题我按 X 假设，影响是 Y，你可以后面推翻”。
5. 对照停止判据（下表）决定停或继续。

### B 写规格

1. 复制 `references/spec-template.md` 的骨架，逐块填。
2. 功能列表分三级（核心 / 次要 / 边界情况），每级用判据确认，不靠感觉。
3. 约束与偏好分开列：约束必须写明**来源**且可被第三方验证；偏好必须写出**档位取舍**。
4. 每条功能点配至少 1 条正例验收 + 1 条否定用例验收，按 `references/spec-template.md` 的“可判定命题”句式写。
5. 接口定义补齐常被漏掉的：错误码表、幂等性、重试语义、版本兼容策略。
6. 走一遍脱敏检查（见下），顶部集中列假设与风险。

### C 拆任务卡片

1. 按可独立交付的结果拆，不按“先写后端再写前端”这种工序拆。
2. 每张卡片填齐必填字段；验收标准引用规格条目编号 **并附摘要**（防止规格变更后卡片静默失效）。
3. 画依赖：依赖只写“缺它做不了”的，不写“相关”的。
4. 自查：每条验收标准都有卡片承接；每张卡片的验证命令都能被复制执行。

## 停止判据（何时算澄清够了）

全部满足才可停：

1. 每条功能点都能写出至少 1 条可判定验收标准（正例 + 否定用例）。
2. 每条约束都注明了来源，且可被第三方验证；偏好的档位已选定，或显式标为“待定（由 X 决定）”。
3. 无残留的开放枚举词：等等 / 尽量 / 可能 / 视情况 / 友好 / 优秀。
4. 范围边界明确：有非空的“本次不做”（outOfScope），且用户确认过。
5. 所有未知都以【假设】显式标注，每条假设附“若为假的影响 + 复查触发点”。
6. 剩余未知只影响实现细节，不影响验收判定。

**不要停（继续拷问）的信号**：用户还在用形容词描述需求；同一需求里有两个互相矛盾的目标；出现“看情况”；验收阈值没人拍板。

## 【坑点】（只写模型容易猜错的）

- **伪需求**：用户说的往往是方案而非问题。信号是出现具体技术/控件名（“加个弹窗”“上 Redis”）却说不出触发条件。拷问句：“如果去掉这个，什么问题依然存在？”存在 → 那是伪需求。
- **把偏好说成约束**：用户说“必须用 PostgreSQL”，其实只是熟悉。判据是问：“违反这条，方案是被**否决**还是被**扣分**？”否决=约束，扣分=偏好。
- **验收标准写成愿望**：“登录要安全”不可判定；“连续 5 次密码错误后第 6 次返回 429 且锁定 15 分钟”可判定。判定法：两个人独立按此判据执行，是否得到同一个 passed/failed。
- **不可验证的条目不该当标准**：写成风险或待办，不要混进验收列表充数。
- **否定路径被系统性遗漏**：空值、极值、并发、超时、部分失败、重复提交、权限不足、依赖不可用 —— 每个功能至少覆盖一条。
- **不要替用户编约束**：凭空指定合规等级、并发量、SLA 是把假设伪装成事实，必须标【假设】。
- **范围蔓延靠变更记录兜住**：规格每次修改都记“日期 / 改了什么 / 为什么 / 谁定的”，否则卡片与规格会静默脱钩。
- **不要重造调度**：任务依赖、并行、验收门禁交给宿主 plan mode / AgentTeams，本技能只产出它们的输入。

## 失败处理（用户答不上来时怎么降级）

- 不追问超过 2 轮同一问题；第 3 轮改成“候选选项 + 默认值”，让用户选而不是作答。
- 用户说“你定 / 无所谓 / 先这样” → 转成**假设清单**，每条形如：编号 | 假设内容 | 依据（行业惯例 / 最小风险 / 你给的原话） | 若为假的后果 | 复查触发点。
- 影响面分级：**高**（改假设要重做，如核心交互模型、数据模型）→ 必须让用户确认才能进 B；**中/低** → 可带假设前进，但在规格顶部集中列出。
- 假设在拆卡片时必须转成卡片的“风险与假设”字段，不能丢。
- 用户始终无法回答且无法确认高风险假设 → 交付“澄清记录 + 假设清单 + 风险标注”，并明确说明缺哪些输入才能继续。

## 安全

- 规格与卡片中**不得写入真实凭据**：口令、token、私钥、连接串、真实手机号/身份证/客户名一律替换为 `<PLACEHOLDER>` 或 `<从环境变量读取>`。
- 发现用户需求里已含敏感信息时：不要复述原值，直接提示“检测到疑似敏感信息，已脱敏为 X，请确认原值不要进入文档”，并在规格末尾加“脱敏提示”小节。
- 接口定义只写字段名 / 类型 / 来源，不写字段值。

## 【验证】交付前自查清单

- [ ] 每条验收标准都能判定真假（含阈值、单位、触发条件），无“友好/优秀/尽量”。
- [ ] 每条功能点都有 ≥1 条正例 + ≥1 条否定用例验收。
- [ ] 每条约束都有来源且可被第三方验证；偏好有明确档位。
- [ ] 每条验收标准都有对应任务卡片承接（编号可追溯）；每张卡片都能追回规格条目。
- [ ] 无残留“待定/TBD/待确认”项；如有，均已转为带影响与复查触发点的【假设】。
- [ ] outOfScope 非空，且用户确认过。
- [ ] 没有真实凭据；含敏感信息处已脱敏并给出提示。
- [ ] 规格内无开放枚举词（等等 / 诸如 / 必要时）。
- [ ] 未写代码、未编排任务；依赖与调度已明确移交宿主。
- [ ] 规格有变更记录小节。
