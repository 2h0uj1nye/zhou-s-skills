# 模式 C：任务卡片模板（Ticket Template）

卡片的目标：**下游（人或 Agent）拿到就能独立开工，不需要回头再问一次**。缺字段 = 把成本转移给下游。

## 卡片模板

```markdown
## T3 <动词开头的标题，一个可交付结果>

- **目标**：<一句话，可验证：做完后什么从“不是”变成“是”>
- **依赖**：T1（缺它做不了：<具体缺什么>）｜ 无
- **范围（可改动）**：`path/a`、`path/b`
- **范围外（禁止改动）**：`path/c`、公共配置、其他模块
- **交付物**：<文件路径 / 接口名 / 产物名，可核对>
- **承接规格条目**：AC-4（连续 5 次失败锁定 15 分钟）、F3（并发提交去重）
- **验收标准**：
  - [ ] <可判定命题，直接抄规格并附编号>
  - [ ] <否定用例：权限不足时返回 403 且不产生记录>
- **验证方式**：<可复制执行的命令或步骤> —— 预期输出：<具体结果>
- **风险与假设**：<来自规格第 0 节的假设编号；若假设为假怎么处理>
- **估算**：M（半天～1 天）｜ 不确定度：低
```

## 必填字段及理由（为什么少一个就会被误解）

| 字段 | 缺了会怎样 |
|---|---|
| 编号 + 标题 | 无法被引用，无法作为依赖目标；口头沟通时指代不清 |
| 目标（一句话可验证） | 标题只有名词（“登录模块”）时，实施者自行发明目标 |
| 依赖（含“缺什么”） | 只写“相关”会让两个任务并行冲突，或做出错误顺序 |
| 范围 / 范围外 | 没有范围外，实施者顺手重构无关模块，diff 失控、review 失效 |
| 交付物（可核对） | “完成登录功能”无法核对；“`src/auth/login.ts` 导出 `login()`”可以 |
| 承接规格条目 | 无法追溯需求覆盖；规格改了卡片也不会被发现 |
| 验收标准（可判定） | 自称完成，无法复核；争议时无仲裁依据 |
| 验证方式（可执行 + 预期输出） | “跑一下测试看看”不可执行；必须给命令与期望结果 |
| 风险与假设 | 假设被静默当成事实，返工在最后暴露 |
| 估算 + 不确定度 | 无法排期；高不确定度的任务被当成确定的 |

**选填**：优先级。只有在已有明确排期上下文时才填；否则不要硬编“高/中/低”—— 那是假信息。

## 拆解规则

1. **按可独立交付的结果拆**，不按工序拆。“先写后端再写前端”不是任务，是顺序。
2. **粒度判据**：一张卡片应能在一次专注工作中完成，且能被单独验证（≥1 条可判定验收）。超出 → 继续拆；小到没有独立可验证结果 → 合并。
3. **独立性**：卡片完成后，其验收标准不依赖“其他未完成卡片”才能判断。做不到 → 依赖没写对。
4. **覆盖检查**：规格里每条验收标准都必须被至少一张卡片承接；反之每张卡片的验收标准都应能追回规格条目（编号 + 摘要）。
5. **引用要带摘要**：只写 `AC-4` 会在规格修改后静默失效；写 `AC-4（连续 5 次失败锁定 15 分钟）`，规格一改就能看出脱钩。

## 依赖书写规则

- 依赖只写**缺它做不了**的前置；“有点相关”不写。
- 写清缺什么：`T1（缺它做不了：登录接口的返回结构未定）`，而不是 `T1`。
- 无依赖写“无”，不要留空 —— 留空无法区分“没有依赖”和“忘了写”。
- 循环依赖 = 拆分错误，回到第 1 条重拆。
- **不做排期与调度**：依赖关系写出来即可，执行编排交给宿主 plan mode / AgentTeams。

## 验证方式写法

- 形式：可复制执行的命令或可照做的手工步骤 + **预期输出**。
- ✗ “跑一下测试看看”
- ✓ `bash -c "npm test -- auth"` —— 预期：`login.lock.spec` 6 项全绿
- ✗ “手工验证登录”
- ✓ 手工：用错误密码连续提交 5 次 → 第 6 次返回 429；等待 15 分钟后正确密码可登录

## 反例（字段缺失导致的典型事故）

- 无范围外 → 实施者顺手升级了公共依赖，引入不相关问题。
- 无验证方式 → 卡片被标完成，实际未达验收，返工推迟到集成阶段。
- 依赖写成“相关” → 两条任务并行改动同一文件，冲突解决时丢失验收语义。
- 验收标准只写编号 → 规格更新后卡片悄悄失效，无人察觉。
- 一张卡片塞两个结果（“做登录**和**发验证码邮件”）→ 部分完成无法表达，卡片长期挂起。
