# 需求规格与拆解（requirements-planning）

> 一句话：把「做个登录」「优化一下体验」这种一句话的模糊想法，逼成能验收的规格文档和能直接开工的任务卡片。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH 技能。纯 Markdown 指令包，文件里没写平台限制，Linux / macOS / Windows 都能用 |
| 外部依赖 | 零依赖：不用装软件、不用配置文件、不联网、不调用任何外部工具 |
| 产出 | 三选一：澄清记录 + 假设清单 / 规格文档 / 任务卡片集，都写成 .md 文件 |
| 入选理由 | 它卡在所有项目最上游的那道口子——需求没想清就开工；而且自带"问到什么程度算够"的判据，不会无限追问下去 |

## 它解决什么问题

大多数需求是含着说的：「做个登录」背后可能是单点登录、可能是手机验证码、也可能只是给内部用的一个口令框。不澄清就直接写，写完才发现做的是用户脑子里另一版东西，返工成本全砸在最后。这个技能干的事就是把你脑子里的隐性判断逼成显式文字：先问清意图，再写成每条都能判定真假的规格，最后拆成下游拿到就能开工的卡片。它的目标是让交接给别人的输入是干净的，而不是自己顺手把活也干了。

## 什么时候该用它

- 「我想做个能自动整理笔记的小工具」——只有一句话，细节全在你脑子里。
- 「帮我把这个需求写成规格文档」——你已经想清楚了，只差落成正式文档。
- 「这些需求你帮我拆成任务，分给几个人做」——规格有了，缺可执行的卡片。
- 「优化一下体验」这种听起来很宏大、但没人能说清做完算不算成功的说法。

## 什么时候别用它

- 你已经给出了明确规格，只是在问「这个怎么实现」——那是技术问答，不是需求澄清。
- 纯代码调试、查 API 用法、报错排查——跟需求无关，别绕这一圈。
- 你要的是排期、优先级排序、任务派发和依赖调度——本技能明确不管，那是宿主自带能力（plan mode / AgentTeams）的事。
- 只是想快速聊个想法、还没打算落地；或者你已经想清楚了，只是要一句「怎么实现」。

## 怎么开口

- 「我想做个登录功能，你先问清楚我要什么，别急着写。」
- 「帮我把这个想法写成规格文档，验收标准要能判定真假。」
- 「规格我已经有了，帮我拆成任务卡片，每张卡要能独立验收。」
- 「这份需求你审一下，哪些验收标准其实是没法判断的？」

## 输入 / 输出

**它向你要**：需求原文（你的原话，最好别提前润色）+ 已知硬约束（预算、截止时间、已有系统或接口、合规要求、技术栈锁定）。可选的有目标用户、成功指标基线、现有方案的痛点。

**它给你什么**：看你走到哪一步。

- 澄清阶段：一份**澄清记录**（问过什么、答了什么、哪些没答上）+ 一份**假设清单**，每条假设都带「依据 / 若为假的后果 / 什么情况下要回来复查」。
- 规格阶段：规格文档，含功能列表（核心 / 次要 / 边界情况三级）、约束条件、接口定义（错误码、幂等性、重试语义、版本兼容）、验收标准、假设与风险、脱敏提示、变更记录。
- 拆卡阶段：任务卡片集，每张卡片目标 / 依赖 / 可改动范围 / 禁止改动范围 / 交付物 / 承接的规格条目 / 验收标准 / 验证命令 / 风险与假设齐全。

## 依赖与前提

无。不需要任何软件、账号或网络，产物就是几个 Markdown 文件（默认放在你指定的路径，没指定就放当前工作目录，命名如 `spec-<主题>.md`、`tickets-<主题>.md`）。

## 内部结构

- `SKILL.md` 129 行：定位与边界、三个模式的路由规则、停止判据、失败降级处理、安全红线、交付前自查清单。
- `references/interrogation.md` 114 行：模式 A 的细则——五类问题（伪需求 / 约束与偏好 / 失败模式 / 验收预演 / 范围取舍）、提问话术、假设清单格式。
- `references/spec-template.md` 125 行：模式 B 的规格骨架、可判定验收标准句式与正反例对照。
- `references/ticket-template.md` 71 行：模式 C 的卡片模板、必填字段及其理由、拆解粒度与依赖书写规则。

这样拆的原因：主文件只留路由和判据（每次都要读），三大块模板各自成文件，只在走到那一步时才加载，省上下文也便于以后单独改模板。

## 注意事项与已知限制

- **它不会自动把三步跑完**：你只要规格，它就不会顺手把卡片也拆了，更不会替你写代码；反过来你要规格时，它会先跑一个最简版澄清（最多 3 个问题），答不上来就退回规格补。
- **同一个问题最多追问 2 轮**：第 3 轮改成「我先按 X 假设，影响是 Y，你后面可以推翻」。影响面高的假设（核心交互模型、数据模型这类）必须你确认才能继续，中低影响的可以先带着走但在规格顶部集中列出——所以文档里出现假设清单是正常现象，不是它偷懒。
- **它的产出质量上限由你决定**：你答不上来的部分，它只会标成假设，不会替你编。凭空指定合规等级、并发量、SLA 这种事它有明确红线禁止。
- **文档里不会出现真实凭据**：口令、token、私钥、连接串、真实手机号和身份证会被替换成占位符，发现你贴了敏感信息还会提示你脱敏。

## 来源

由 3 个技能合并而来：**反向拷问（grill-me）** + **需求规格化（to-spec）** + **任务拆解（to-tickets）**。合并时补上了原三者都缺的两块：一是「什么时候该停止追问」的停止判据（6 条全满足才算澄清够），二是「用户答不上来时怎么降级」（同一问题最多问 2 轮，之后转成带后果与复查触发点的假设清单，按影响面分高/中/低）。同时明确去掉了排期与任务调度——那属于宿主自带能力。以上来源取自移交说明；`SKILL.md` 与三个 references 正文里都没写明这三个旧技能的名字，文件内查不到合并痕迹。
