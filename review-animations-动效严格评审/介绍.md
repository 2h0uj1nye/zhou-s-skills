# 动效严格评审（review-animations）

> 一句话：拿 Emil Kowalski 的高标准去挑你这次改动里的动画代码毛病，默认先开火、通过要自己挣，最后给一个明确的「Block / Approve」判决。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零依赖。不需要联网、不需要 CLI、不需要 npm 包；`STANDARDS.md` 只是本地参考文件。但它面向 Web（CSS / Framer Motion / Base UI 这一类）动画代码 |
| 产出 | 一份纯文本评审，固定两段：① 一张 `Before / After / Why` 三列表格（一行一个问题点）；② 按影响层级分组的裁决，结尾给 **Block** 或 **Approve** |
| 入选理由 | 治的是「动画能跑就算过」的病。模型默认对动画很宽容，这个技能把「跑得动」和「手感对」拆开，并且给了一整套可引用的硬数值（具体 cubic-bezier、每类元素的毫秒预算、spring 参数），让挑刺有据可依，而不是凭感觉说「有点慢」 |

## 它解决什么问题

大多数动画代码「能跑」，但手感是错的：过渡发虚、入场从错误的位置飞出来、在高频操作上乱动、掉帧。技能正文把标准写死了：那种「跑得动但迟钝、原点错、触发太频繁、掉帧」的过渡**算回归（regression），不算通过**。

它的默认姿态就是挑毛病——"Default to flagging. Approval is earned, not assumed."。评审方法借的是攻击性极强的代码质量评审那一套：不可谈判的标准、见即升级的触发条件、修复优先级阶梯、分层输出、明确的通过标准。

判断标准的来源是 Emil Kowalski 的动画哲学（animations.dev），十条不可谈判的标准覆盖：动效是否正当、频率是否匹配、缓动是否响应式、是否 300ms 以内、原点与物理正确性、可打断性、是否只动 GPU 属性、可访问性、进出不对称、与产品气质是否统一。

## 什么时候该用它

- 「帮我评审一下这个动效改动」「我这个下拉菜单的动画有没有问题」
- 「review 一下这个 PR 里的动画代码」
- 「这个过渡感觉不太对，你帮我看看哪里错了」
- 「这段 Framer Motion 写法有性能问题吗」
- 「这个 modal / drawer / toast 的动画达标吗」

## 什么时候别用它

- **评审的不是动画代码**：技能明确写了，被要求评审通用代码时要**拒绝**并指向一个通用评审技能。它不写功能、不修无关 bug。
- **要审计整个代码库、要一份动效修复路线图**：用 `improve-animations`。这个技能只管**单个 diff**。
- **要发动画机会（该动却没动的地方）**：用 `find-animation-opportunities`。
- **要从零实现一个动画**：用 `animate`。
- 它是 `disable-model-invocation: true`，**只能被显式调用**，不会自动触发。

## 怎么开口

- 「按高标准评审一下我这次改的动画代码，这是 diff」+ 贴代码
- 「review 一下 `Dropdown.tsx` 的入场动画，用 review-animations 的标准」
- 「这个按钮按下的反馈动画哪里不对？」
- 「`transition: all 300ms ease-in` 这样写行吗？」（它会直接判 Block 级别的点）
- 「帮我看看这个 toast 的动画能不能过审」

## 输入 / 输出

**输入**：你贴的动画 diff 或具体代码片段，外加你的问题。首次被调用且**没有具体问题时**，技能规定了固定开场白，只回这一句：

> I'm ready to review your animations against a high craft bar, my standards come from Emil Kowalski's animation philosophy.

在用户提问之前**不给任何其他信息**。

**输出**必须是固定的两部分，顺序不能变：

**Part 1 — Findings 表格（必需）**：单张 markdown 表格，一行一个问题，列是 `Before | After | Why`。技能明确禁止写成 "Before:/After:" 列表。每行给「现在是什么 → 应该改成什么 → 为什么」。数值要从 `STANDARDS.md` 里取原文，不许近似。

**Part 2 — Verdict（必需）**：剩余意见按影响层级从高到低分组，空层省略：
1. **Feel-breaking regressions** — 迟钝的缓动、凭空冒出来、在高频/键盘操作上触发
2. **Missed simplifications** — 本该删掉或大幅削减的动画
3. **Performance** — 非 GPU 属性、掉帧风险、样式重算风暴
4. **Interruptibility & timing** — 该用 transition/spring 却用了 keyframes；该不对称却对称
5. **Origin, physicality & cohesion** — 原点错、气质不搭、生硬的交叉淡入
6. **Accessibility** — reduced-motion 与 hover 门控

结尾**必须给明确判决**：
- **Block** — 任何 feel-breaking 回归、键盘/高频操作上的动画、UI 上的 `scale(0)` 或 `ease-in`、或一个容易改成 GPU 却还在动非 GPU 属性的动画。
- **Approve** — 没有 feel-breaking 回归、没有明显该删的动效、时长与缓动在范围内、需要处已处理可打断性、尊重了 reduced-motion。

引用要具体到 `file:line`，需要给具体数值时从 `STANDARDS.md` 里取。

## 依赖与前提

零外部依赖，但要读懂它得先读同目录的 `STANDARDS.md`。判定依赖语境：技能要求区分「高频」和「偶发」元素，所以你得能说明这个元素多久被看到一次；也需要知道项目用什么栈（CSS transition / Framer Motion / Base UI 等）才能给对修复方案。面向 Web，React Native 不在它的范围内。

## 内部结构

包由两个文件组成：

- `SKILL.md` — 评审的**姿态、方法、输出格式**。
- `STANDARDS.md` — 精确数值的**规则目录**，技能的引用源，在需要精确值或引用时加载。

`SKILL.md` 正文的核心机制有四块：

1. **十条不可谈判标准**：正当性 / 频率匹配 / 响应式缓动 / sub-300ms / 原点与物理正确 / 可打断 / 只动 GPU 属性 / 可访问性 / 进出不对称 / 气质统一。
2. **见即升级的触发条件（14 条）**：`transition: all`、`scale(0)` 或纯淡入无初始 transform、UI 上的 `ease-in`、键盘快捷键或 100+/天的操作上有动画、UI 时长 > 300ms 无理由、trigger 锚定的 popover 却 `transform-origin: center`、toast/开关上跑 keyframes、动布局属性、页面繁忙时用 Framer Motion 的 `x`/`y`/`scale`、在父元素上更新 CSS 变量去驱动子元素 transform、移动缺少 `prefers-reduced-motion`、未门控的 `:hover` 动效、按压-释放却对称计时、该 30–80ms stagger 却齐刷刷一起进场。
3. **修复偏好阶梯（9 级，从早到晚）**：① 删掉动画 → ② 削减（更短/更小/更少属性）→ ③ 修缓动 → ④ 修原点与物理感 → ⑤ 改为可打断 → ⑥ 搬到 GPU → ⑦ 不对称计时 → ⑧ 打磨（blur、stagger、`@starting-style`、spring）→ ⑨ 可访问性与气质。**偏好越靠前的动作。**
4. **分层输出 + 明确判决**（见上一节）。

`STANDARDS.md` 里给出的具体硬数值包括：频率决策表（100+/天 = No animation. Ever.）、缓动决策顺序（进出→`ease-out`，屏幕内移动→`ease-in-out`，悬停/变色→`ease`，匀速→`linear`，默认→`ease-out`；**UI 上永远不用 `ease-in`**）、三条强曲线（`--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`、`--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`、`--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1)`）、时长表（按钮按压 100–160ms、tooltip/小 popover 125–200ms、下拉/选择 150–250ms、modal/drawer 200–500ms）、spring 参数（Apple 风格 `{ type: "spring", duration: 0.5, bounce: 0.2 }`，bounce 保持 0.1–0.3）、手势规则（动量关闭用速度而非距离阈值，`Math.abs(distance)/elapsedMs > ~0.11`）、stagger 30–80ms、blur 掩蔽交叉淡入 `< 20px`，以及调试建议（慢放 2–5×、逐帧看、真机测手势、隔天用新鲜的眼睛看）。

## 注意事项与已知限制

- **默认挑刺**：别期待它说「挺好的」。通过是挣来的，不是默认的。
- **会拒绝越界请求**：被要求评审非动画代码时要拒绝并指向通用评审技能；它不写功能、不修无关 bug。
- **弹窗例外**：modal 居中显示，`transform-origin: center` 对它是**正确的**，不该被报为问题。
- **不确定时的建议**：技能自己说，当不确定动效手感对不对时，最好的做法往往是**删掉它**；或者建议慢放/逐帧回看、隔天再看，而不是瞎猜。
- **无固定开场白之外的话术**：首次无提问调用时只回那一句固定英文，不额外展开。
