# 过度设计审查（ponytail-review）

> 一句话：不看你代码对不对，只看你代码**多余不多余**——哪段能删、该用什么替代、删完能少多少行，最后给你一句"净减 N 行"。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为中文） |
| 外部依赖 | 零依赖。它只读代码、只出报告，不装任何东西、不需要联网和 key |
| 产出 | 一份清单，一行一条：`<标签> <该删什么>. <用什么替代>. [位置]`，结尾一句 `net: -N lines possible.` |
| 入选理由 | 常规代码审查都在找 bug，几乎没人系统地找"多余"。它把这个盲区做成了一个有固定输出契约、有五种判定标签、还能顺着 `ponytail:` 注释查历史欠账的工具 |

## 它解决什么问题

代码跑得对，不代表它值得存在。一个"只有一个实现的接口"、一个"只做转发"的包装层、一个"没人设过"的配置开关，都不会让测试变红，却会一直收利息——每次改动都要多看几个文件。这个技能就是专门来收这笔账的：它不看正确性、不看安全、不看性能，只问一句"这东西删了会怎样"，并给出替代写法。

## 什么时候该用它

- "帮我 review 一下这段改动，看看有没有过度设计。"
- "这堆代码能删掉什么？"
- "审计一下整个仓库，哪儿最臃肿？"
- "我之前推迟了哪些简化？给我列个 ponytail 债务清单。"
- "这个 PR 是不是写复杂了？"

## 什么时候别用它

- **你想找的是正确性 bug、安全漏洞、性能问题**——这些明确不在它的范围内，它会指路让你走常规代码审查。
- **不是编程任务**——写作、翻译、答疑别用。
- **你想让它顺手把代码改了**——它默认只出报告、不动代码。只有你明确要求，而且只在你确认过的那几条上动手。
- **工作区里没有任何改动，而你只说了"review 一下"**——这种情况它会自己切到全库审计并说明原因，结果范围可能比你预期的大。

## 怎么开口

- "review 一下当前改动，只挑多余的。"
- "审计整个仓库，按能删掉多少行排序。"
- "我这一堆 `ponytail:` 注释现在什么情况了？"
- "这条建议我不想听空话，给我具体该换成什么。"

## 输入 / 输出

三种模式要的东西不同：**diff 审查**要当前工作区的改动（你也可以指定某个 commit 或分支范围）；**全库审计**要仓库根目录，你可以额外告诉它哪些目录跳过；**债务台账**要仓库根目录加上这个项目用的注释前缀（默认认 `#` 和 `//`）。它不需要你提供别的东西。

输出是**严格一行一条、先给最大的删减项**（代码块那行就是唯一格式）：

```
<标签> <该删什么>. <用什么替代>. [位置]
```

位置写法：单文件写 `L<行号>`，跨文件或全库写 `<路径>:L<行号>`。**结尾必须给唯一指标**：`net: -<N> lines possible.`；确实没有可删的就写 `Lean already. Ship.` 然后停手。全库模式多给一个依赖维度的数字：`net: -<N> lines, -<M> deps possible.`。债务模式的收尾不同：`<N> markers, <M> with no trigger.`，干净时写 `No ponytail: debt. Clean ledger.`

五种标签是全局共用的判定标准：`delete:` 死代码、没人用的灵活性、投机功能（替代：无）；`stdlib:` 手写了标准库已有的东西（**必须点名是哪个函数**）；`native:` 依赖或代码在做平台本来就做的事（**必须点名那个平台特性**）；`yagni:` 只有一个实现的抽象、没人设的配置、只有一个调用方的层；`shrink:` 同样逻辑更少行数（要给出更短的写法）。

## 依赖与前提

无。不需要装软件、不需要 key、不需要联网。唯一的"前提"是你得在一个代码仓库里——它要看 diff、看目录树、或者 grep 注释。

## 内部结构

`SKILL.md` 只有 79 行，是个瘦路由层：一张"用户说法 → 哪个模式 → 扫什么范围 → 读哪个细则文件"的表，加上全局共用的输出契约、五个标签的定义、坑点、交付前自查清单。三份细则各管一个模式：`references/diff-review.md`（30 行）是改动的判定清单加 5 组正反例；`references/repo-audit.md`（26 行）是全库狩猎清单与"按删减量降序、不看文件大小"的排序规则；`references/debt-ledger.md`（34 行）给出那条 `grep -rnE '(#|//) ?ponytail:' .` 扫描命令、台账格式（被简化了什么 + ceiling 天花板 + upgrade 什么时候回头）与腐化标记。

这样拆的理由是**省上下文**：三种模式共用同一套标签和输出格式，所以契约只写一遍；每个模式真正的扫描清单不同，又互不干扰，用哪个读哪个。

## 注意事项与已知限制

- **最小测试不算臃肿**：单个冒烟测试或 `assert` 自检是极简技能的底线，明令禁止建议删除。这是最容易被误伤的一条。
- **不许给空泛建议**：坑点里点名批评"这个类可能有点复杂，你考虑下是否必要？"这种说法，要求必须给一句可执行的替代；没有替代方案才写 `Nothing replaces it.`
- **只列清单、不自动改代码**，用户明确要求时才动手；**全库模式的排名依据是"删掉能减多少行 / 多少依赖"**，不是文件大小，并确认已跳过 `node_modules`、`.git`、构建产物。
- **债务台账有个"腐化"标记**：写了 `ponytail:` 却没写升级路径或触发条件的注释会打上 `no-trigger` 标签——这批就是会悄悄烂掉的欠账，也是这个模式最有价值的输出。台账默认只读，你要求落盘时才写出文件（如 `PONYTAIL-DEBT.md`）。
- **需要责任人时它会用 `git blame -L<行号>,<行号>` 去查**，所以在没有 git 历史的目录里这项能力会退化。
- 它有一句恢复指令：说 "stop ponytail-review" 或 "normal mode" 就切回常规审查口吻。

## 来源

**由三处内容合并而成**：原来的 review（审查当前改动）、整仓审计 audit、以及债务台账 debt。后两者现在是本技能的**两个模式**，各占一个 reference 文件，第三个文件仍是默认的 diff 审查。合并时去掉的是重复——三种模式原本各有自己的标签体系和输出格式，现在统一收进主文件的一套契约，只保留扫描范围的差异。

需要指出的是：这三条合并来源在 `SKILL.md` 里**没有留下合并说明或溯源标注**，文件里只有"三种模式"的功能描述，读不出它们曾经是三个独立技能。这是文档层面的一个缺口；要追溯只能从功能对应关系上认出来（模式三 ↔ debt-ledger、模式二 ↔ repo-audit）。
