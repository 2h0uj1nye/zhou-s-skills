# Sonner 吐司指南（ask-sonner）

> 一句话：Sonner（React toast 库）的用法与排障手册，从挂载 `<Toaster />`、选对 `toast()` 调用，一直到「toast 不出现 / 出现两次 / 样式丢失 / 深色模式不跟随」这类疑难。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零硬依赖；面向使用 `sonner` npm 包的 React（或 Next.js/Astro 等）前端项目 |
| 产出 | 对话内的用法指导、代码片段，以及一张「症状 → 原因与修法」的排障表 |
| 入选理由 | Sonner 的坑很集中又很反直觉：`theme` 默认 `'light'` 且不跟随系统、第二個 `<Toaster />` 会让每条 toast 出现两次、注入样式优先级赢过 Tailwind、Shadow DOM 里样式丢失。这些是模型的默认知识里最容易答错的地方，而这份内容出自作者 Emil Kowalski 本人 |

## 它解决什么问题

Sonner 只有两个部件——一个挂在根部的 `<Toaster />` 和任意客户端代码里调用的 `toast()`——但几乎所有问题都出在「多挂了一个」或「调错了地方」。技能开头就把这两件事钉死：`<Toaster />` **只挂一次、尽可能靠近根**（Next.js 放 `layout.tsx`，它能在 server component 里工作），**绝不能按页面挂或条件渲染**，否则第二条 toast 会被复制一份；`toast()` 是纯函数、不需要 hook 或 provider，但**在服务端什么也不做**，所以 server action 里要 `return` 结果、在客户端拿到结果后再调 `toast()`。

接着是一张「你想要什么 → 调哪个」的对照表：纯文本用 `toast('标题')`（加 `{ description }` 就是第二行）、带图标用 `toast.success/error/info/warning`、自己管状态时的转圈用 `toast.loading` 再按 id 更新、跟着 promise 走的用 `toast.promise(promise, { loading, success, error })`（`success`/`error` 可以接函数，拿到 resolve 值或 error）、要按钮用 `{ action: { label, onClick } }`（点完默认关闭，除非 `onClick` 里调 `event.preventDefault()`）、完全自定义 JSX 但保留壳用 `toast(<jsx />)`、完全无样式用 `toast.custom((t) => <jsx />)`。

样式部分它给了一个**升级阶梯**，并规定「只爬到改动需要的高度；一上来就跳到顶层没问题（那本来就是推荐的终态），卡在中间不行」：① 默认 + `richColors`（彩色成功/失败）/`invert`；② 内联微调 `toastOptions={{ style }}`；③ 给部件加类名 `toastOptions={{ classNames: { toast, title, description, actionButton, cancelButton, closeButton } }}`——注意 **Sonner 注入的样式会赢过级联，所以每个类都得 `!important`**（Tailwind 写 `!text-red-900`），如果被逼得标了一堆 `!important` 就该停手，改走 ④ headless：用 `toast.custom()` 保留定位/堆叠/滑动行为，自己写 JSX，并包一层你自己的 `toast()` 抽象——这是给设计系统做 toast 的推荐做法。

排障表覆盖了 13 种症状：从不出现、出现两次、Tailwind 类失效、完全无样式（Astro、view transitions 常见，需要显式 `import 'sonner/dist/styles.css'`）、Shadow DOM 里无样式（要把含 `[data-sonner-toaster]` 的 style 标签拷进 shadow root）、被弹窗遮挡或被裁剪（祖先创建了层叠上下文，把 `<Toaster />` 移到 document root）、深色模式被忽略（`theme` 默认 `'light'`，要传 `theme="system"` 或 `resolvedTheme`）、成功/失败还是灰的（那是默认，要加 `richColors`）、永不关闭（`duration: Infinity`、`dismissible: false` 或 promise 永不 settle）、`toast.promise` 卡在 loading、滑动方向不对（由 `position` 推导，用 `swipeDirections` 覆盖）、每条 toast 出现在所有 toaster 里（多 toaster 需要 `id` + `toasterId`）、移动端离屏幕边缘太近（`offset` 默认 32px、`mobileOffset` 默认 16px）。

## 什么时候该用它

- 「Sonner 的 toast 一直不出现，帮我查一下」
- 「同一条 toast 弹了两次是怎么回事？」
- 「我给 toast 加的 Tailwind 类完全没生效」
- 「怎么让 Sonner 跟着我的深色模式切？」
- 「上传文件要 loading 然后成功/失败，怎么写？」
- 「toast 被我的模态框挡住了，或者被裁掉了」

## 什么时候别用它

- 要**从零挑一个 toast/通知库**时，用 `pick-ui-library`——它的清单里 toast 这一格指名的就是 Sonner。
- 要整套界面设计/动效打磨决策用 `emil-design-eng`；苹果式流体动效方法论用 `apple-design`。
- 不是 Sonner 的 toast 问题（比如自己手写的 toast 组件）不属于本技能范围。

## 内部结构

目录里有两个文件，是典型的「正文 + 速查手册」切分：

- **`SKILL.md`（约 90 行）**：主正文。依次是开场白、Setup（两条铁律）、Picking the right call（8 行对照表）、Recipes（更新/常驻/关闭/读活跃 toast、文本里放链接或组件、多 toaster、关闭回调）、Styling 的四级升级阶梯、Icons/Theme、Troubleshooting（13 行症状表）。
- **`API.md`（约 64 行）**：精确的 prop 表。三张表——`<Toaster />` 的 16 个 prop（含默认值，如 `theme` 默认 `'light'`、`position` 默认 `'bottom-right'`、`visibleToasts` 默认 3、`gap` 默认 14、`hotkey` 默认 `⌥/alt + T`）、`toast()` 的 20 个 option（`duration` 默认 4000ms、`dismissible` 默认 true、`containerAriaLabel` 默认 `'Notifications'` 等）、以及函数表（`toast.*`、`toast.dismiss`、`toast.getActiveToasts`、`useSonner()`）。并说明了一条优先级规则：`toast()` 传入的选项会覆盖 Toaster 上 `toastOptions` 里的同名项。

之所以分开：主文件负责「该怎么做」，API 文件负责「精确叫什么」，避免正文被表格淹没，需要时才加载。

## 注意事项与已知限制

- **只挂一个 `<Toaster />`**；挂两个（layout 和 page 各一个）会让每条 toast 出现两遍。
- `toast()` **只在客户端有效**；server action 里要返回结果、由客户端调用。
- React StrictMode 开发模式下 effect 双调用也会造成重复，修法是改从事件处理器触发，或传稳定的 `id` 让第二次调用变成更新。
- **Sonner 注入的默认样式优先于你的类**，`classNames` 必须配 `!important`（Tailwind 用 `!` 前缀）；标得太多就说明该换 headless。
- `theme` 默认 `'light'` **不跟随系统**，要显式传 `theme="system"` 或 `resolvedTheme`。
- 成功/失败默认不是绿的/红的，要加 `richColors`。
- 有两个彼此独立的关闭回调：`onDismiss`（关闭按钮或滑动）和 `onAutoClose`（超时），**没有单一的 "closed" 回调**。
- `toast.promise` 需要真正的 promise（或返回 promise 的函数）且必须 settle，否则 loading 状态永远停在那。
- 技能只做指导，不自动改你的代码。
