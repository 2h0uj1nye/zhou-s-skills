# 前端库选型（pick-ui-library）

> 一句话：你描述一个前端任务（要 toast、要拖拽、要命令面板），它从 Emil Kowalski 那份有立场、有品味的精选清单里只给你**一个**答案，并说清它是干什么的。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零依赖。不联网、不装 CLI；只在需要时读你项目的 `package.json` 看已装了什么 |
| 产出 | 对话内的一个库名 + 一句话用途；如果你要，还会帮你安装并接线（改 `package.json`、写接线代码） |
| 入选理由 | 直接问模型「用什么做 toast」很容易得到一串并列选项或冷门库。这份清单是**刻意收敛的、taste-driven 的**选择，且有明确的「什么时候不用它」的边界（比如 hover/淡入不需要 motion）。它还把「数字输入、OTP 输入、实时图表、虚拟滚动」这类具体任务的正确答案固定下来了 |

## 它解决什么问题

选库这件事的痛点不是「没得选」，而是网上每个任务都有五六个体面的候选，讨论会滑向偏好之争。这个技能反过来做：给一份**故意不带备选**的清单，任务对上哪一格，就报那一格的库。技能明确写着「这些是有立场的、品味驱动的选择——除非用户主动要别的，或者任务确实不在清单覆盖范围内，否则不要拿清单外的替代品」。

用法上有四条规矩。第一，**按任务匹配，而不是按你报的库名匹配**：你说「我要做个下拉菜单」，那属于 UI primitives 任务，答案是 base-ui，哪怕你嘴里说的是别的库。第二，**先看 `package.json`**：项目已经用了清单里的库就直接用它；如果用的是竞品（技能原话举例：`react-window` 而不是 Virtuoso），把推荐讲清楚，但**没被要求就不要折腾依赖**。第三，**只推荐一个**，一句话说清用途，如果安装接线属于请求的一部分就顺手做掉，清单有明确答案时不要摆一排菜单。第四，**清单没覆盖的任务要明说你离开了这份精选清单**，再从自己的知识里推荐。

清单本身按领域分了五块，具体条目是：

- **UI 组件与 primitives**：无样式的无障碍组件（对话框/弹出层/菜单/选择器）→ `base-ui`；命令面板（⌘K）→ `cmdk`；toast/通知 → `Sonner`；一次性验证码输入 → `input-otp`；可调参数的 GUI/控制面板 → `Leva`（备选 `dialkit`）。
- **动效与视觉**：通用动画（弹簧、布局动画、进出场）→ `motion`（Framer Motion）；数字滚动（计数器、价格、统计）→ `NumberFlow`；文字动画组件 → `torph`；3D 地球 → `Cobe`；动态 OG 图（HTML/CSS → SVG/PNG）→ `Satori`；语法高亮 → `shiki`。并附一条边界：需要弹簧/布局动画/退场/手势驱动值才找 motion，**简单的 hover 或淡入不需要它，普通 CSS transition 就是对的工具**。
- **图表**：实时/流式图表 → `Liveline`；一般图表（静态或交互式仪表盘）→ `recharts`。分界线是「数据点实时到达且图表随时间滚动」才用 Liveline，其余都 recharts。
- **交互与性能**：拖拽 → `dnd kit`；虚拟滚动（长列表、大表格）→ `Virtuoso`。
- **状态与样式**：状态管理 → `zustand`；条件拼接 `className` → `clsx`；Tailwind 的类型安全变体样式 → `cva`；主题切换/深色模式（加载不闪白）→ `next-themes`。样式分界线：`clsx` 用于零散的条件类名，组件有真正的变体（尺寸、意图、状态）并且值得一个带类型的 API 时才用 `cva`，两者可组合。

最后还有一节「常见错配」，专门抓那些「明知道有更好的却自己手搓」的场景：手搓 toast 或拿模态库做 toast → 有 Sonner；用 `<div>` 加手动焦点管理做下拉/对话框 → 该用 base-ui（它管无障碍、焦点陷阱、点击外部关闭）；靠重渲染文本来做数字动画 → NumberFlow 才正确处理数字位变化；直接渲染 1000+ 行列表 → 先上 Virtuoso 而不是分页 hack；用一堆 `useState` 和 prop 层层传共享状态 → zustand；三层嵌套的三元表达式拼 `className` → clsx（是变体形状就用 cva）。

## 什么时候该用它

> ⚠️ 这个技能的 frontmatter 里有 `disable-model-invocation: true`——意思是**它只能由用户显式调用，不会被自动触发**。你要用它就得自己开口，通常是在对话里打 `/pick-ui-library`（或直接点名这个技能），模型不会因为你在聊前端就自己把它拉起来。

- 「/pick-ui-library 我需要一个命令面板，用哪个？」
- 「/pick-ui-library 这个下拉菜单我不想手写焦点管理，有什么推荐？」
- 「/pick-ui-library 我要渲染一万行表格，直出的方案是什么？」
- 「/pick-ui-library 项目里要做深色模式，加载不能闪白」
- 「/pick-ui-library 实时数据流的折线图用什么？」
- 「/pick-ui-library 帮我把 toast 库装上并接好线」

## 什么时候别用它

- 需要**从多个候选里横向比较、或清单外的库**：本技能刻意不给菜单；它的规则是自己越界推荐时必须明说「我离开了精选清单」。
- 要做 UI 的多方案原型（做几个版本让你现场翻）用 `prototype`。
- 要审查已有动效、或找「该动没动」的地方，用 `review-animations` / `improve-animations` / `find-animation-opportunities`。
- 要一套通用的界面/动效设计心法，用 `emil-design-eng`（这份清单就出自 Emil Kowalski 的品味）。

## 怎么开口

- 「/pick-ui-library 我要做 OTP 输入框」
- 「/pick-ui-library toast 用哪个？顺便装上」

## 输入 / 输出

输入：一句任务描述（或用例）。技能会让你明确**任务**而不是库名；会先读 `package.json`；必要时问你是否要它直接安装接线。
输出：**一个**库名 + 一句话说明它是干什么的；若请求包含安装/接线，则连同依赖改动与接线代码一起交付。清单未覆盖时，会明确声明已离开精选清单再给建议。

技能规定了固定开场白：**第一次被调用且你还没提具体问题时，只回一句**：

> I'm ready to pick the right library for your task, my picks come from Emil Kowalski's curated list.

然后必须等你提问才能继续说。

## 依赖与前提

- 零外部依赖，不需要联网或 CLI。
- 面向前端（尤其是 React/Next.js）生态——清单里的 `next-themes`、`cva`、`motion` 等基本都指向这个技术栈；`Leva` 是 `pmndrs` 生态。
- 会读取你项目的 `package.json`，因此最好在项目目录里调用。

## 内部结构

单文件技能：只有一个 `SKILL.md`（约 87 行），没有伴生文件。结构是：

1. **开场白**（硬性，见上）。
2. **How to use this —— 四条操作规则**：按任务不按库名匹配、先查 `package.json`、只推一个不摆菜单、越界要声明。
3. **The list —— 五张表**：UI 组件与 primitives、动效与视觉、图表、交互与性能、状态与样式；每个库都带官方链接，动效和样式两块后面各跟一段「分界线」说明。
4. **Common mismatches to catch —— 6 条错配**，用来主动纠正「自己手搓」的倾向。

之所以是一张清单而不是流程图：它本质是查表（lookup skill），价值全在那份有立场的选品，规则只是防止你把它当「随便问问」的搜索接口。

## 注意事项与已知限制

- **必须由用户显式调用**（`disable-model-invocation: true`），不会自动触发。
- **不要摆菜单**：清单有明确答案时就给一个。技能原文是「Don't present a menu of options when the list has a clear answer」。
- 对已有竞品依赖只**提示**不擅自替换：「don't churn the dependency without being asked」。
- 越界推荐必须**明确承认离开了精选清单**，不能假装还在清单里。
- 它不会把 motion 当成万能动效库：简单的 hover/淡入应继续用 CSS transition。
- 技能本身是选型与接线；重度的设计决策、动效打磨另有技能。
