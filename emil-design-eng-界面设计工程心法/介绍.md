# Emil Kowalski 界面设计工程心法（emil-design-eng）

> 一句话：把「这个界面哪里不对劲」变成一张 `Before | After | Why` 表格，每个改动都给出具体属性、具体曲线、具体毫秒数。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用；技能正文为英文，不影响使用） |
| 外部依赖 | 零依赖，单文件纯文本方法论。面向 Web 前端：CSS、React、Framer Motion、Base UI、Sonner。不联网也能用（只偶尔引用 easing.dev / easings.co 作为曲线来源）。 |
| 产出 | 审查 UI 代码时输出固定格式的 markdown 表格 `| Before | After | Why |`（一行一个问题）；回答设计细节时给出可直接粘贴的 CSS / JSX 片段与数值。不写文件、不改代码。 |
| 入选理由 | 它治的是「界面没坏但就是不好用」这种没有报错信息的病。模型默认会写 `transition: all 300ms`、`ease-in`、`scale(0)`、`transform-origin: center` 这些看着眼熟但手感错的代码；这份技能把 Emil Kowalski 的规则变成硬性约束（鼠标按下的 3% 缩放、100–160ms、强曲线 `cubic-bezier(0.23, 1, 0.32, 1)`），并强制用表格给差评，杜绝「提升体验」式空话。 |

## 它解决什么问题

软件「能用」已经不值钱了，剩下的是手感。这个技能开篇就摆出三条主张：**品味是练出来的，不是天生的**（好品味不是个人偏好，是可以训练出的识别力——多看好作品、反问它为什么好、反复练）；**看不见的细节会复利**（引 Paul Graham：「一千个几乎听不见的声音齐声合唱」——大多数细节用户永远不会注意到，这正是目标）；**美是杠杆**（大家功能都够用了，好的默认值和好的动画才是差异点）。

具体到日常，它治的是几类高频错误。第一类是**该不该动没想清楚**：技能要求先问「用户一天看几次」，100+ 次/天的操作（键盘快捷键、命令面板开关）**永远不要动画**——Raycast 就没有开合动画，这是每天用几百次的东西的最优解。第二类是**动效配料错**：`ease-in` 会让界面显得迟钝（它在用户盯得最紧的那一刻故意不动），所以 UI 里**永不用 ease-in**；CSS 内置缓动太弱，要用 `--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`、`--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`、`--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1)`（iOS 抽屉曲线，来自 Ionic）。第三类是**感知性能**：180ms 的下拉比 400ms 的「更灵敏」，转得更快的加载圈让同一个加载时长「感觉更快」；UI 动画守则是不超过 300ms。

第四类是那些没人会单独注意到、但合起来决定成败的零件：按钮 `:active` 必须有 `transform: scale(0.97)`（0.95–0.98 之间）配上 160ms；**绝不能从 `scale(0)` 进场**（现实里没有东西从虚无中出现，要从 `scale(0.95) + opacity: 0` 起步）；popover 要 `transform-origin: var(--transform-origin)` 从触发它的按钮长出来，**modal 是唯一例外**（它不挂在触发点上，保持居中）；第一个 tooltip 之后相邻 tooltip 要瞬间打开（`[data-instant] { transition-duration: 0ms }`）。

最后它还给了一条贯穿性判断：**用户在做决定的阶段可以慢，系统在回应的阶段必须快**（长按删除按下 2s linear、松手 200ms ease-out），以及「第二天再回看自己的动画」——把时长调到 2–5 倍或逐帧播放，才看得见全速下看不见的时序问题。

## 什么时候该用它

- 「这个下拉菜单感觉有点肉，哪里不对？」
- 「帮我审一下这段 UI 代码，看看有没有手感问题。」
- 「弹窗打开的时候要怎么进场才自然？该给多少毫秒？」
- 「这个按钮点下去没反应感，怎么改？」
- 「我做个 toast，动画用 keyframes 还是 transition？」
- 「拖拽关闭抽屉怎么做才跟手？」

## 什么时候别用它

- 要**从零写一个新动画的实现**，用 `animate`（Web）或 `animate-expo`（React Native）——那是施工技能，本技能是心法与评审。
- 要**严格评审已有动画**（逐条判定合格/不合格），用 `review-animations`；本技能的表格更偏「直接给改法」。
- 要**扫描整个代码库**产出动效改进路线图，用 `improve-animations`；要**找哪些地方该动却没动**，用 `find-animation-opportunities`。
- 任务其实是**选一个 UI 组件库**（toast、drawer、命令菜单、dropdown），用 `pick-ui-library`——手搓这些正是得到「一个没有焦点管理的 `<div>` 下拉」的原因。

## 输入 / 输出

输入：UI 代码、组件片段，或一句对交互细节的困惑。技能**没有前置提问**流程，直接进入判断。

输出有严格规定：**评审 UI 代码时必须用 markdown 表格**，列为 `| Before | After | Why |`，一行一个问题；技能明确点名了错误格式（把 `Before:` / `After:` 写成两行列表）并说「never do this」。典型行如 `transform: scale(0)` → `transform: scale(0.95); opacity: 0`，理由「Nothing in the real world appears from nothing」。除表格外，回答会直接给可粘贴的 CSS/JSX 代码与具体数值。

**固定开场白**：技能被首次调用且用户没有具体问题时，只回一句 ——「I'm ready to help you build interfaces that feel right, my knowledge comes from Emil Kowalski's design engineering philosophy.」在此之前不提供任何其他信息。

## 依赖与前提

无网络、无 CLI、无 npm 包要求。约定的技术栈偏 Web：原生 CSS（`@starting-style`、`clip-path`、`transform-style: preserve-3d`）、React 与 Framer Motion（`useSpring`、`useReducedMotion`）、Base UI 的 `var(--transform-origin)`、Web Animations API。文中以 Sonner 和 Vaul 作为实现范例。

有一条明确的运行时提醒：若 `@starting-style` 浏览器不支持，退回 `data-mounted` 属性模式（`useEffect(() => setMounted(true), [])`）。

## 内部结构

只有一个 `SKILL.md`（676 行），没有伴生文件。按「为什么 → 怎么审 → 怎么决策 → 怎么建组件 → 怎么测」推进，核心机制是四段式结构：

- **Core Philosophy**：三条主张（品味可训练、细节复利、美是杠杆）。
- **Review Format (Required)**：强制的 `Before | After | Why` 表格格式，附正反例。
- **The Animation Decision Framework**：四个必须按顺序回答的问题——(1) 该不该动（频率表：100+/天不动 → 几十次/天大幅削减 → 偶尔/标准 → 罕见/可加惊喜）；(2) 目的是什么（空间一致性、状态指示、解释、反馈、防止突兀变化五类合法目的）；(3) 用什么缓动（决策树 + 三条自定义曲线，永不 ease-in）；(4) 多快（按元素给时长表，UI 守住 300ms）。之后是 Spring Animations（何时用弹簧、Apple 式 `{ type: "spring", duration: 0.5, bounce: 0.2 }`、bounce 控制在 0.1–0.3、弹簧被打断时保留速度而 keyframes 归零）。
- **实战手册式章节**：Component Building Principles（7 条）、CSS Transform Mastery、`clip-path for Animation`（inset 形状、标签页完美配色过渡、长按删除、滚动揭示、前后对比滑块）、Gesture and Drag Interactions（速度 > 0.11 即可判定 dismiss、边界阻尼、指针捕获、多点触控保护、摩擦而非硬墙）、Performance Rules（只动 transform/opacity、CSS 变量会继承到全部子元素所以不要用父级变量驱动子元素、Framer Motion 的 `x`/`y`/`scale` 简写**不是**硬件加速的，要写完整 `transform` 字符串）、Accessibility（`prefers-reduced-motion` 是「更少更轻」而非「全关」；hover 动画要包在 `@media (hover: hover) and (pointer: fine)` 里）、The Sonner Principles（6 条做被喜爱的组件的原则）、Stagger（30–80ms 间隔）、Debugging Animations（慢放 2–5 倍、逐帧、真机测试）。

结尾是一张 **Review Checklist** 表（11 行），把最常见的问题和对应修法一次列出，例如 `transition: all` → 指名属性；`scale(0)` → `scale(0.95) + opacity: 0`；键盘操作上的动画 → 整个删掉。

**分工**：本技能是本系列的主技能，定位是「品味与判断的源头」——它既下判断（该不该动、用什么曲线、多少毫秒），也管评审格式。具体施工交给 `animate`（Web 动画实现）与 `animate-expo`（React Native/Expo 动画）；严格逐条评审已有动画交给 `review-animations`；全库审计交给 `improve-animations`；找动效机会交给 `find-animation-opportunities`；组件选型交给 `pick-ui-library`。`animate` 明确写了它执行的标准就是本技能这套哲学、也就是 `review-animations` 执行的标准。

## 注意事项与已知限制

- **评审必须用表格**，且必须包含 `Why` 列；写成两行列表是明确的错误格式。
- **硬性禁忌**：`transition: all`；`scale(0)` 进场；UI 元素上的 `ease-in`；键盘触发动作上的动画；触发点锚定的 popover 用 `transform-origin: center`（modal 豁免）；时长超过 300ms 且无正当理由；没有 `prefers-reduced-motion`；未加媒体查询的 hover 动画；在快速重复触发的元素上使用 keyframes；Framer Motion 的 `x`/`y` 简写在高负载下掉帧。
- **blur 上限 20px**，重度 blur 很贵，Safari 尤甚；只用来弥合那些调参数也调不好的 crossfade。
- `prefers-reduced-motion` 不是「全关」：保留透明度与颜色过渡，去掉位移与位置动画。
- 本条技能是**只读的心法与判断**，不会自动修改文件；所有结论以代码片段和表格形式给出，由你决定是否落地。
- 有些事它明确承认给不出公式：列表进出场时 opacity 与 height 的配合、crossfade 的最终手感，靠「调到手感对，然后第二天再看一遍」。
