# 设计令牌规范文件（design-md）

> 一句话：帮你写一份叫 `DESIGN.md` 的"设计说明书"，把品牌用哪几个颜色、什么字体、按钮什么圆角写成人和机器都能读的规范，顺带用官方工具检查颜色对比度是否达标。

| 项目 | 内容 |
|---|---|
| 宿主 | DSH（Ubuntu 24.04 实测可用 / 校验、导出用的命令行工具需要 Node.js，本机未实测，见下） |
| 外部依赖 | 写文件零依赖；`lint` / `diff` / `export` 需要 Node.js 的 `npx`（首次运行要联网下载 `@google/design.md`）；不需要 API key |
| 产出 | 一份 `DESIGN.md`（YAML 令牌 + Markdown 说明）；可选 `tailwind.theme.json` 与 `tokens.json`；以及 lint / diff 检查结果 |
| 入选理由 | 是 Google 的公开规范且有官方命令行工具可验证——对比度、坏引用、章节顺序都能机器判定，不是"看着差不多就行" |

## 它解决什么问题

让 AI 做页面时颜色全凭它当场的喜好，这次靛紫、下次蓝绿，同品牌的几个页面放一起就不像一家人。
根子在于设计规范通常只存在于 Figma 文件、聊天记录或某个人脑子里，AI 读不到。
`DESIGN.md` 把规范落成一个纯文本文件——上半部分给机器看（精确色值、字号），下半部分给人看（为什么这么定、怎么用），两者同处一个文件，谁都不会跑偏。

## 什么时候该用它

- "帮我写一份 DESIGN.md / 设计规范 / 设计令牌文件。"
- "我几个项目的视觉想统一，怎么让 AI 每次都按同一套来？"
- "这是现有的 DESIGN.md，帮我校验 / 看看改这版有没有变差 / 导出成 Tailwind。"
- "帮我检查这套配色的对比度，够不够无障碍标准。"
- "把我们的品牌风格指南转成 AI 能直接读的格式。"

## 什么时候别用它

- 你要的是**页面成品**或**界面审计**（出 HTML、给方案、看哪里有问题）——那是 `design-toolkit` 的活。
- 你只是想找视觉灵感或布局参考——它管的是规范文件的编写，不做样式创意。
- 你要做 PPT / 演示文稿——那是 `univer-slide` 的领域。
- 你还没确定设计方向，只想"先随便看看效果"——先出方案比先立规范更合适。

## 怎么开口

- "帮我写一份 DESIGN.md：品牌调性偏克制，主色深墨蓝，强调色一点砖红，字体用 Public Sans。"
- "校验一下我这份 DESIGN.md，有错直接改掉。"
- "把这份 DESIGN.md 导出成 Tailwind 主题和 DTCG 的 tokens.json。"
- "帮我看看这套颜色搭配的对比度够不够 WCAG AA。"

## 输入 / 输出

**它会向你要：** 品牌调性、想要的主色与强调色、字体方向（也可以直接给一个网址、一张图或几个氛围词，它负责翻译成规范写法）；如果是改已有文件，就把文件给它。

**最后给你：** ① 一份 `DESIGN.md`——**上半部分 YAML**（一种严格的"键: 值"格式）写精确令牌：颜色、字号、圆角、间距、组件；**下半部分 Markdown** 写人话说明，章节固定为：概述 → 颜色 → 字体 → 布局 → 层级与阴影 → 形状 → 组件 → 该做与不该做。② 可选 `tailwind.theme.json`、`tokens.json`（W3C 设计令牌格式）两个导出文件。③ 检查结果：坏引用、重复标题、非法色值/尺寸、对比度是否达到 WCAG AA（4.5:1）和 AAA（7:1）。

## 依赖与前提

**写文件**无依赖，纯文本；**校验与导出**需要 Node.js，命令形如 `npx -y @google/design.md lint DESIGN.md`，`npx` 会临时下载执行、不用全局安装，因此**首次运行需要联网**。不需要任何 API key。生成的文件授权随用户项目走，规范本身是 Apache-2.0。

## 内部结构

`SKILL.md` 199 行 + `templates/starter.md` 99 行，**没有 references**。
`starter.md` 是一份带完整示例值和注释的空白模板（颜色、字体、圆角、间距、组件都有，八个正文小节齐全），拿到就能往里填。
不拆 references 的原因：这个技能的"细则"就是 Google 那份规范本身，官方命令行工具还能直接打印规则（`npx -y @google/design.md spec --rules-only --format json`），再抄一份进技能只会两边不同步。

## 注意事项与已知限制

- **规范还是 alpha 版**（文件里写 `version: alpha`），官方明确可能出破坏性改动，长期依赖要留意。
- **组件变体不许嵌套**：`button-primary-hover` 要写成和 `button-primary` 平级的条目，写成 `button-primary.hover` 是错的。
- **十六进制颜色和负数字号必须加引号**：`"#1A1C1E"`、`letterSpacing: "-0.02em"`；不加引号 YAML 会读错甚至截断。
- **章节顺序被强制**，重复标题会让整个文件判不合格；顺序乱了要先重排再保存。
- **令牌引用要写完整路径**：`{colors.primary}` 可以，`{primary}` 不行。
- **本机未实测 `npx` 那几条命令**：文档写了但没在这台机器上真跑过，node 环境与网络都会影响结果，首次使用请留出下载时间。
- **正文里有一处过时指引**：SKILL.md 让你"想做一次性的 HTML 设计就去找 `claude-design`"，但那个技能在本批目录里已不存在（被合并进 `design-toolkit`），照它说的会落空；frontmatter 的 `related_skills` 里也还挂着这个名字。
- 它只做规范和令牌，**不产出任何页面**，别指望它给你一个能打开的 HTML。
